## 4. Task 1 - Map the local network configuration

### Why this matters

Before interpreting a packet capture, I need to know which interface is active and where the operating system sends traffic that is not on the local subnet. Otherwise, it is easy to select the wrong interface or misunderstand the packet direction.

### Procedure

Run:

```bash
ip -brief addr
ip route
ip route get 1.1.1.1
```

How to read the output:

- `ip -brief addr` gives a compact list of interfaces and assigned addresses. Look for an interface that is up and has an address used for the current network.
- `ip route` displays the routing table. The default route usually begins with `default via` and identifies the next-hop gateway and outgoing interface.
- `ip route get 1.1.1.1` asks the kernel which route it would use for that destination. It is a route lookup, not a connectivity test.

Record the interface name, address family, local address in a private notebook, default gateway, and selected egress interface. Do not publish a home or workplace IP address.

If using WSL2, note that the visible interface and gateway may belong to a virtualised network. Record that context rather than assuming it is the physical Wi-Fi adapter.

### Evidence to collect

- Command used.
- Relevant interface and route fields, with identifying values redacted.
- One sentence explaining why the selected interface should see the test traffic.

## 5. Task 2 - Make and inspect a DNS query

### Why this matters

DNS is already documented in [DNS investigation](./notes/dns-investigation.md). Here I am using a query as a known event that I can correlate with packets in the capture.

### Procedure

Run an A-record query:

```bash
dig example.com A
```

Then run an AAAA-record query:

```bash
dig example.com AAAA
```

Read the output:

- The `QUESTION SECTION` shows the requested name and record type.
- The `ANSWER SECTION` contains returned records, if any.
- `SERVER` identifies the resolver that answered the client.
- `Query time` is the resolver response time as reported by dig.
- The status line indicates whether the response was successful, empty, or an error.

Do not assume that the resolver performed a fresh recursive lookup. It may have answered from cache. An empty AAAA answer is not automatically a DNS failure; the queried name may simply have no AAAA record.

If `dig` reports a timeout, record the exact error and check the configured resolver before changing network settings. Do not switch to an unrelated third-party resolver just to force a result.

### Evidence to collect

Record query name, type, response status, answer type, resolver (redact if private), and query time. Keep the output in your local notes if it includes internal details.

## 7. Task 4 - Inspect the capture in Wireshark

### Open and orient yourself

Open the file:

```bash
wireshark week01-network.pcap
```

The packet list shows one row per captured packet. Select a packet and expand the packet details pane to inspect the protocol layers. The bytes pane shows the packet bytes and their offsets.

### DNS analysis

Apply:

```text
dns
```

Find the query generated in Task 2. Select it and inspect:

- DNS transaction ID.
- Query name.
- Query type.
- Whether recursion was desired.

Find the corresponding response. Compare the transaction ID and question section, then inspect the response code and answer records. A matching query and response should be correlated using more than just the domain name.

If the DNS packets are not visible, possible explanations include encrypted DNS, resolver caching at another layer, capture on the wrong interface, or a query that occurred outside the capture window. Record what happened; do not manufacture a packet sequence.

### TCP handshake analysis

Clear the DNS filter and apply:

```text
tcp.flags.syn == 1
```

This displays packets with SYN set. To focus on the connection to TCP port 443:

```text
tcp.port == 443 && tcp.flags.syn == 1
```

Select a candidate initial SYN. Note its source address and port and destination address and port. Use those values to narrow the view to that flow. For example, replace the sample values below with the values from the selected packet:

```text
ip.addr == 192.0.2.10 && tcp.port == 443
```

The address above is documentation-only example space; it is not an expected result from this lab.

Inspect the packets in timestamp order:

1. Client SYN: SYN is set and ACK is normally not set.
2. Server SYN-ACK: both SYN and ACK are set.
3. Client ACK: ACK is set; SYN is not set.

Use the TCP sequence and acknowledgement fields to understand how each side acknowledges the other's initial sequence number. Do not identify packets only by colour or row order; inspect the TCP flags and fields.

Useful filters:

| Display filter | What it isolates |
| --- | --- |
| `tcp` | TCP packets |
| `udp` | UDP packets |
| `dns` | DNS packets decoded by Wireshark |
| `tcp.flags.syn == 1` | Packets with SYN set |
| `tcp.flags.ack == 1` | Packets with ACK set |
| `tcp.flags.fin == 1` | Packets with FIN set |
| `tcp.flags.reset == 1` | Packets with RST set |
| `tcp.port == 443` | TCP packets using port 443 |
| `tcp.analysis.retransmission` | Packets Wireshark identifies as retransmissions |

### Connection termination

For the same flow, inspect the end of the exchange. A graceful TCP close commonly includes FIN and ACK packets in both directions. A reset uses RST. A capture may not include teardown if the capture stopped early, the application reused a connection, or the connection remained open.

Do not treat a missing FIN as proof of an abnormal close. State whether the teardown was actually captured.

### HTTPS visibility

Use Follow TCP Stream if useful to inspect the conversation structure. Expect TLS-protected application data to be encrypted. You may see connection metadata and TLS handshake information depending on the capture, but do not expect the HTTP page body to be readable merely because the packets are visible.

## 8. Task 5 - Produce a small Python summary with Scapy

### Why this matters

Wireshark is useful for manual inspection. A script makes a simple analysis repeatable and gives me a starting point for more careful PCAP tooling. The script below counts selected TCP flags and directional 4-tuples. It does not reconstruct sessions or prove that a connection succeeded.

### Set up an isolated Python environment

From the lab directory:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install scapy
```

On Windows PowerShell, activation is usually:

```powershell
.venv\Scripts\Activate.ps1
```

Save this script as `tcp_analysis.py`:

```python
from collections import Counter
from scapy.all import rdpcap, IP, TCP

CAPTURE_FILE = "week01-network.pcap"

packets = rdpcap(CAPTURE_FILE)
flag_counts = Counter()
directional_flows = set()
tcp_packet_count = 0

for packet in packets:
    if IP not in packet or TCP not in packet:
        continue

    tcp_packet_count += 1
    flags = int(packet[TCP].flags)

    if flags & 0x02:
        flag_counts["SYN"] += 1
    if flags & 0x10:
        flag_counts["ACK"] += 1
    if flags & 0x01:
        flag_counts["FIN"] += 1
    if flags & 0x04:
        flag_counts["RST"] += 1

    directional_flows.add((
        packet[IP].src,
        packet[TCP].sport,
        packet[IP].dst,
        packet[TCP].dport,
    ))

print(f"Captured packets: {len(packets)}")
print(f"IPv4 TCP packets: {tcp_packet_count}")
print(f"Unique directional 4-tuples: {len(directional_flows)}")

for flag_name in ("SYN", "ACK", "FIN", "RST"):
    print(f"{flag_name} packets: {flag_counts[flag_name]}")
```

Run it:

```bash
python tcp_analysis.py
```

### Interpret the output correctly

- `Captured packets` is the number of packets Scapy read from the file.
- `IPv4 TCP packets` counts packets containing both IPv4 and TCP layers. IPv6 TCP packets are not included by this version.
- A directional 4-tuple is source IP, source port, destination IP, and destination port. The reverse direction is a different tuple.
- Flag counts count packets where a bit is set. A single packet can contribute to more than one flag count. For example, SYN-ACK increments both SYN and ACK.
- Retransmitted SYN packets can increase the SYN count.
- These counters do not identify unique connections, completed handshakes, or application success.

If the script errors, record the complete error message and investigate the file path, virtual environment, package installation, and capture format. Do not replace an error with an invented output.

### Evidence to collect

## 11. Interpretation and limitations

A packet capture is evidence of what was visible at one capture point during one time window. It is not a complete view of the network.

Potential limitations include:

- The capture started after a connection was established.
- The capture ended before teardown.
- Traffic used a different interface or network namespace.
- DNS was answered from a local cache or used an encrypted transport.
- Packet loss occurred before or during capture.
- Offloading can affect how packets appear to local capture tools.
- The script ignores IPv6 and does not reassemble streams.
- A port number does not, by itself, prove which application generated the traffic.

The conclusion should distinguish direct observations from interpretations and unresolved questions.

## Desk-based analysis completion (2026-11-25)

**Status:** Analysis questions completed from TCP specifications and the documented loopback socket experiment. Live packet-level evidence remains pending.

This section completes the conceptual analysis without presenting an uncaptured packet sequence as an observed result. The earlier execution record confirms a local application-level exchange, but no PCAP was created in that environment.

### Analysis answers

1. **Interface and route:** The documented socket experiment was bound to `127.0.0.1`, so the relevant path was the host's loopback interface, not a physical network adapter. The recorded endpoints were both in the IPv4 loopback range. The original DNS/HTTPS capture procedure has not been run, so its selected egress interface, default gateway, and DNS route remain unknown.
2. **DNS query and response:** The procedure asks for A and AAAA records for `example.com`. No DNS command output or packet capture is attached to the execution record, so the actual response status, answer records, resolver, and query time cannot be stated.
3. **Matching DNS messages:** In a capture, I would correlate a response with its query using the DNS transaction ID and question section (name, type, and class), then check direction and timing. Matching only the domain name is insufficient when multiple queries are present.
4. **Start of TCP connection:** The initial SYN is the packet that requests a new TCP connection. It normally has SYN set and ACK clear. The local socket experiment did not capture this packet, so no frame number can be reported.
5. **SYN-ACK acknowledgement:** The server's SYN-ACK has both SYN and ACK set. Its acknowledgement number is the client's initial sequence number plus one, acknowledging the SYN. The server also supplies its own initial sequence number.
6. **Final ACK:** The client's final ACK acknowledges the server's SYN by acknowledging the server's initial sequence number plus one. It completes the three-way handshake and establishes the connection for normal bidirectional data transfer.
7. **Connection teardown:** The socket experiment showed a TIME-WAIT entry after the client closed, which is consistent with TCP teardown state. However, without a capture I cannot identify the FIN/ACK exchange, determine which endpoint sent the first FIN, or provide packet numbers. A socket state is not a substitute for packet-level evidence.
8. **HTTPS visibility:** The IP and TCP headers remain visible to an ordinary packet capture, and parts of the TLS handshake may also be visible. Application data is protected by TLS encryption, so the HTTP body and protected headers are not normally readable from the capture alone.
9. **Why SYN count can exceed successful connections:** The script counts every IPv4 TCP packet with the SYN bit set. It can count retransmitted SYNs, half-open attempts, failed connections, and SYN-ACK packets. It also counts SYN-ACK as SYN because both flags are set. Therefore, it is a packet counter, not a successful-connection counter.
10. **Script limitations:** It parses IPv4 only, ignores IPv6, treats the two directions as separate 4-tuples, does not track connection state, does not reassemble TCP streams, and counts flag bits rather than completed handshakes. It also relies on Scapy successfully reading the capture. Its output is a compact summary, not a full TCP session analysis.

### Investigation challenge - repeated SYN without SYN-ACK

Plausible explanations include a destination that is not responding, filtering on the path or host, routing failure, packet loss, an incorrect destination address or port, or a capture point that sees outbound packets but not the return path. A capture that began or ended at the wrong time can also make the exchange look incomplete.

To investigate further, I would verify the selected route, confirm the destination and service are correct, inspect the local firewall rules read-only, compare captures from an authorised endpoint if available, and check whether the destination is known to be listening. A single endpoint capture cannot locate the loss or prove which device discarded a packet.
